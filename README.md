## 💡 О проекте

**Цифровые финансовые активы (ЦФА)** — цифровые права (например, денежные требования),
которые выпускаются, учитываются и обращаются в информационной системе на основе
распределённого реестра. В России их регулирует закон **259-ФЗ**.

Проект — работающий прототип такой информационной системы (ОИС):

| Участник | Что делает на платформе |
|---|---|
| 🛡 **Администратор (оператор ИС)** | Проверяет анкеты и допускает участников, модерирует «Решения о выпуске», следит за блокчейном и сверкой, формирует отчёты |
| 🏢 **Юрлицо — эмитент** | Заполняет «Решение о выпуске» по образцу оператора ИС, после одобрения собирает заявки и закрывает сбор (DvP) |
| 👤 **Физлицо — инвестор** | Пополняет кошелёк, покупает ЦФА с подтверждением СМС-кодом (ПЭП), видит портфель, скачивает выписки |
| 🏦 **Юрлицо — инвестор** | Покупает ЦФА без годового лимита, подписывает заявки «УКЭП» |
| 🧑‍💼 **Индивидуальный предприниматель** | Выпускает свои ЦФА, как юрлицо (259-ФЗ, ст. 2 ч. 3), и покупает чужие: лимит 600 000 ₽ в год как у физлица, подпись «УКЭП» |

**Ключевые идеи:**

- **Допуск через администратора.** Пока анкета не одобрена, участник видит только свой профиль. Одобрение включает его адрес в **белый список смарт-контракта**.
- **Модерация выпусков.** Эмитент заполняет документ из 15 разделов по образцу «Решения о выпуске». На витрину выпуск попадает только после проверки администратором.
- **Настоящий DvP на EVM.** Деньги инвесторов замораживаются в смарт-контракте. При закрытии сбора **одна транзакция** либо поставляет ЦФА всем и переводит деньги эмитенту, либо возвращает деньги всем.
- **Понятно, выгодно ли покупать.** У каждого выпуска — доходность к погашению, премия к ОФЗ того же срока, сравнение с вкладом и оценка 0–100. Эмитент видит то же самое прямо во время заполнения документа.
- **Два уровня учёта, которые сверяются.** Каждая операция пишется и в SQLite, и в блокчейн. Админ-панель построчно сверяет их и формирует акт сверки.

## ✨ Возможности

<table>
<tr><th>Раздел</th><th>Что умеет</th></tr>
<tr><td><b>🔐 Вход и регистрация</b></td><td>

- Вход по логину и паролю, пароли хранятся только в виде хэша (scrypt)
- Анкета физлица или юрлица с **мгновенной подсветкой ошибок**; физлицо отмечает «Я ИП» — анкета дополняется ОГРНИП и расчётным счётом. Та же проверка повторяется на сервере
- **Подсказки городов** (1117 городов России) для места рождения и адресов, паспорт и ИНН — только цифры
- После регистрации анкета уходит **на проверку администратору**

</td></tr>
<tr><td><b>🛡 Админ-панель</b></td><td>

- Сводка: сколько анкет и документов ждёт решения, объёмы размещения и холда
- **Допуск участников:** вся анкета и **автоматическая сверка** (контрольные суммы ИНН, СНИЛС, ОГРН, ключ счёта по БИК, возраст, дубли паспорта / телефона / e-mail), одобрение, отказ с причиной, блокировка
- **Модерация «Решений о выпуске»:** документ целиком, подсказки модератору, одобрение (→ витрина и смарт-контракт) или возврат на доработку с замечаниями
- **Блокчейн и сверка:** состояние сети, транзакции с методами контракта, построчная сверка учёта с контрактом
- **Журнал действий** администраторов и **отчёты** (реестр участников, акт сверки, журнал в CSV)

</td></tr>
<tr><td><b>📊 Аналитика выпусков</b></td><td>

- На карточке витрины: **доходность к погашению, премия к ОФЗ, срок и оценка 0–100** с вердиктом «Привлекательно / Умеренно / Слабо»
- Страница «Аналитика» выпуска: сравнение с ОФЗ, ключевой ставкой, вкладами и инфляцией, **график купонов**, калькулятор «если вложить N ₽» против вклада, спрос, разбор оценки
- **Живой дашборд в конструкторе** Решения о выпуске: графики и оценка перерисовываются при каждом изменении поля
- Тот же дашборд у модератора; рыночные ориентиры (ключевая ставка, вклады, инфляция, кривая ОФЗ) администратор меняет в админке

</td></tr>
<tr><td><b>📝 Решение о выпуске</b></td><td>

- Форма из **15 разделов** по образцу РоВ оператора ИС: эмитент, оператор, вид и объём прав, количество, цена, период размещения, смарт-контракт, обеспечение, ответственность, круг лиц, риски и подписи
- Обязательные положения **долговых ЦФА** (259-ФЗ ст. 3 ч. 1.2), формула купона и график выплат вставляются автоматически; проверка «Не хватает: …» перед отправкой
- Сведения об эмитенте подставляются из проверенной анкеты, объём выпуска считается на лету
- Отклонённый документ эмитент исправляет и отправляет повторно
- SHA-256 документа записывается в смарт-контракт — документ и токен связаны

</td></tr>
<tr><td><b>⛓ Блокчейн</b></td><td>

- Смарт-контракт **CFAPlatform** на Solidity: белый список KYC, токенизированный рубль, выпуски, заявки с холдом, атомарный DvP
- **Встроенная EVM-сеть** (py-evm) — без Node.js и отдельных узлов; журнал транзакций воспроизводится при запуске
- **Самовосстановление**: если транзакция БД откатилась после транзакции в EVM, сеть пересобирается из журнала
- Можно подключить внешний узел: Anvil, Hardhat, Besu (`EVM_RPC_URL`)

</td></tr>
<tr><td><b>📄 PDF-документы</b></td><td>

- Для администратора: анкета с результатами проверки, реестр участников, акт сверки с блокчейном

</td></tr>
<tr><td><b>👛 Личный кабинет</b></td><td>

## 🚀 Быстрый старт

**Нужно:** Python 3.9–3.13. Node.js не нужен: блокчейн работает внутри Python.

<details open>
<summary><b>🪟 Windows (PowerShell)</b></summary>

```powershell
git clone https://github.com/KISEL4KO/VTB_Hack.git
cd VTB_Hack
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
flask --app main seed-demo     # демо-данные: админ, эмитент, инвесторы, выпуски
python main.py
```
</details>

<details>
<summary><b>🐧 Linux / 🍎 macOS</b></summary>

```bash
git clone https://github.com/KISEL4KO/VTB_Hack.git
cd VTB_Hack
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
flask --app main seed-demo
python main.py
```
</details>

Откройте **http://127.0.0.1:5000**.

**Без демо-данных** — создайте только администратора:

```bash
flask --app main create-admin admin      # спросит пароль
```

**Пересоздать базу с нуля** (удалит все данные, включая журнал блокчейна):

```bash
python database_setup.py
```

> ⚠️ Миграций нет. Если вы изменили схему таблиц в `SCHEMA_SQL`, базу нужно пересоздать этой командой
> или удалить `cfa.db` — иначе сервер будет падать с ошибками вида `no such column`.

> 💡 Если библиотеки блокчейна не установились, платформа всё равно запустится: при запуске будет написано
> «Блокчейн выключен», а учёт продолжит работать на SQLite. Минимальный набор: `pip install Flask reportlab`.

## 🎬 Демо-сценарий для защиты

1. **Регистрация.** В окне инкогнито `/register` → анкета физлица. Покажите подсветку ошибок и подсказки городов. После отправки кабинет показывает «Анкета на проверке».
2. **Допуск.** Войдите как `admin` → «Допуск участников» → откройте новую анкету: автоматическая сверка, кнопка «Одобрить допуск». В ответ приходит хэш транзакции — адрес добавлен в белый список контракта.
3. **Сравните анкеты** `new_company` (предупреждения по контрольным суммам) и `new_ivan` (паспорт уже занят).
4. **Решение о выпуске.** Войдите как `demo_issuer` → «Мои выпуски» → «Новое решение о выпуске». Внизу — «Не хватает: …», кнопка неактивна. В разделе 3 при вводе ставки и дат появляются формула купона и график, ниже — обязательные положения долговых ЦФА. Выберите в разделе 10 «Поручительство» — раскроются поля и подпись поручителя в разделе 15; в разделе 12 — «Только ИП и компании». Отправьте с ошибкой (минимум больше максимума) — поля подсветятся. Исправьте и отправьте.
5. **Модерация.** Как `admin` → «Решения о выпуске» → верните на доработку с замечанием. Эмитент видит замечание и исправляет. Одобрите — выпуск появится на витрине и в смарт-контракте.
6. **Покупка.** Новым инвестором: пополнить кошелёк → «Купить ЦФА» → код **`1234`**. Деньги перейдут в холд — и в базе, и в контракте.
7. **DvP.** Эмитентом «Закрыть сбор»: одна транзакция поставляет ЦФА и переводит деньги.
8. **Купоны.** `demo_issuer` → «Мои выпуски» → «Купоны и погашение» по выпуску 01: график записан в смарт-контракт, у каждой даты — «Сторож выплатит автоматически». `admin` → «Сторож выплат» → «Проверить сейчас»: ближайшая дата ещё не наступила, раньше срока не заплатит ни сторож, ни эмитент, ни сам контракт.
9. **Сверка.** `admin` → «Блокчейн и сверка»: все строки «совпадает». Скачайте «Акт сверки (PDF)».
10. **Аналитика.** На витрине сравните оценки выпусков, откройте «Аналитика» → калькулятор. В конструкторе РоВ поменяйте ставку или периодичность — дашборд перерисуется сразу.
11. **Документы.** Решение о выпуске, итоги выпуска, реестр владельцев, выписка инвестора — всё в PDF.
12. **Перезапуск.** Остановите и снова запустите сервер: в консоли «воспроизведено транзакций: N», сверка по-прежнему сходится.

## ⛓ Блокчейн: лёгкая EVM-сеть и смарт-контракт

### Как устроена сеть

```mermaid
sequenceDiagram
    autonumber
    participant App as Flask (database_setup.py)
    participant Ch as blockchain.py
    participant EVM as EVM (py-evm)
    participant DB as SQLite

    App->>Ch: transact("subscribe", issue, investor, qty, sig)
    Ch->>Ch: nonce оператора = длина журнала? (иначе пересобрать EVM)
    Ch->>EVM: eth_call — «примерка»
    alt require() не прошёл
        EVM-->>Ch: revert «Недостаточно свободных средств»
        Ch-->>App: ChainError → ROLLBACK SQLite
    else всё в порядке
        Ch->>Ch: подписать ключом оператора
        Ch->>EVM: send_raw_transaction → новый блок
        Ch->>DB: INSERT evm_transactions (сырые байты транзакции)
        Ch-->>App: tx_hash → в журнал операций
    end
```

- **Встроенный режим (по умолчанию).** Внутри приложения работает настоящая виртуальная машина Ethereum (`py-evm` через `eth-tester`). Каждая подписанная транзакция сохраняется в таблицу `evm_transactions`. При запуске журнал **воспроизводится** в чистой сети. EVM детерминирована, поэтому адрес контракта, хэши транзакций и состояние получаются ровно такими же. В этом и суть блокчейна: *состояние = журнал транзакций + детерминированная машина*.
- **Самовосстановление.** Все транзакции отправляет оператор, поэтому его nonce обязан равняться длине журнала. Если транзакция SQLite откатилась уже после исполнения в EVM, перед следующей операцией сеть пересоберётся из журнала.
- **Внешний узел.** Задайте `EVM_RPC_URL` (например, `http://127.0.0.1:8545` для [Anvil](https://book.getfoundry.sh/anvil/) или Hardhat, или адрес закрытой сети Besu / Quorum) и при необходимости `EVM_OPERATOR_KEY`. Контракт развернётся при первом запуске.
- **Кастодиальная модель.** Транзакции подписывает оператор платформы по поручению участников, подписанных ПЭП / УКЭП в веб-интерфейсе. Так устроены закрытые сети операторов ИС. У пользователей нет кошельков MetaMask, а их адреса служат идентификаторами в реестре.

### Смарт-контракт `blockchain/CFAPlatform.sol`

| Функция | Когда вызывается | Что проверяет и делает |
|---|---|---|
| `setParticipant(addr, verified, qualified)` | админ одобрил / заблокировал участника | белый список KYC и статус квалификации |
| `depositRub(addr, amount)` | пополнение кошелька | только верифицированным; выпуск токенизированных рублей |
| `withdrawRub(addr, amount)` | вывод | хватает свободных рублей |
| `registerIssue(id, issuer, price, min, max, onlyQual, docHash)` | админ одобрил РоВ | эмитент верифицирован, параметры корректны; хэш РоВ записывается в контракт |
| `subscribe(id, investor, qty, sigHash)` | заявка на покупку | сбор открыт, инвестор в белом списке, квалификация, остаток объёма, деньги → холд |
| `finalize(id)` | эмитент закрывает сбор | **DvP**: ЦФА → инвесторам, рубли → эмитенту; или возврат всем — в одной транзакции |
| `setSchedule(id, start, rateBp, dates[], days[], early)` | сразу после DvP | график купонов в контракт: даты выплат (00:00 МСК), длины периодов, ставка, разрешено ли досрочное погашение |
| `dueAction(id)` | сторож выплат | что пора сделать: 0 — ничего, 1 — купон, 2 — погашение (по времени блока) |
| `payCoupon(id)` | сторож в дату выплаты (или эмитент кнопкой после неё) | дата наступила, купоны по порядку, хватает рублей эмитента; каждому владельцу `qty × цена × rateBp × days / 3 650 000` |
| `redeem(id, accruedDays)` | сторож в дату погашения; эмитент — досрочно | в дату погашения — после всех купонов; досрочно — только если разрешено, номинал + накопленный купон; ЦФА сжигаются |
| `rubBalance`, `rubLocked`, `balanceOf`, `issues`, `investorsOf`, `totalSupply`, `couponsPaid`, `couponOf` | сверка, отчёты | чтение состояния |

Тексты ошибок в `require` написаны по-русски и доходят до пользователя без изменений.

Скомпилированный контракт (ABI и байткод) уже лежит в `blockchain/CFAPlatform.json`. Перекомпилировать нужно только после изменения `.sol`:


## 📊 Аналитика выпусков

Задача — ответить инвестору на вопрос **«стоит ли покупать этот выпуск»**, а эмитенту — **«как мой выпуск увидят инвесторы»**, ещё до отправки на проверку.

### Где видна

| Место | Что показано |
|---|---|
| **Витрина** (`/`) | Купон, доходность к погашению, премия к ОФЗ, срок, оценка 0–100 и вердикт |
| **Страница выпуска** (`/issues/<id>`, кнопка «Аналитика») | Ключевые показатели, сравнение с альтернативами, график выплат и таблица, калькулятор вложения, спрос, разбор оценки, методика |
| **Конструктор РоВ** (кабинет эмитента) | Тот же дашборд в правой колонке — перерисовывается через 120 мс после каждого изменения поля |
| **Модерация** (`/admin/issues/<id>`) | Дашборд рядом с документом: модератор сразу видит аномальную доходность |
| **Рыночные ориентиры** (`/admin/benchmarks`) | Администратор обновляет ставки и кривую ОФЗ; изменение пишется в журнал действий |

### Как считается

Расчёт целиком в браузере — `static/analytics.js` (без зависимостей, тот же модуль используется в тестах на Node.js). Графики — чистый SVG в `static/dashboards.js`.

| Показатель | Формула |
|---|---|
| **График выплат** | Купоны от даты закрытия сбора до погашения с выбранной периодичностью; хвост короче 15 дней присоединяется к последнему периоду |
| **Доходность к погашению** | XIRR — эффективная годовая ставка по всем потокам (цена → купоны → номинал). При ежемесячных выплатах она выше купонной за счёт сложного процента |
| **После НДФЛ** | Купоны × (1 − 13 %); учитывается «заморозка»: деньги блокируются с момента заявки, купон идёт только после закрытия сбора |
| **Премия к ОФЗ** | Доходность ЦФА − доходность ОФЗ того же срока (линейная интерполяция по кривой) — плата за риск эмитента |
| **Калькулятор** | Сумма → целое число ЦФА с учётом минимума / максимума заявки и остатка; сравнение с вкладом под среднюю максимальную ставку на тот же срок, тоже после НДФЛ |

### Оценка 0–100

| Составляющая | Максимум | Логика |
|---|---:|---|
| Премия к ОФЗ | 35 | Растёт до +3 п.п., плато до +7 п.п., дальше снижается: слишком высокая премия — признак высокого риска |
| Срок | 15 | Короткие выпуски надёжнее |
| Обеспечение | 12 | Предусмотрено / нет |
| Спрос | 12 | Сколько собрано относительно минимума выпуска |
| История эмитента | 12 | Состоявшиеся и отменённые выпуски |
| Частота выплат | 6 | Ежемесячно > ежеквартально > раз в полгода > в конце срока |
| Выкуп эмитентом | 4 | Предусмотрен / нет |
| Реальная доходность | 4 | Доходность после НДФЛ выше инфляции |

**70+** — ▲ «Привлекательно», **50–69** — ● «Умеренно», **ниже 50** — ▼ «Слабо». Вердикт всегда подписан словом и значком, не только цветом.

## 📝 Решение о выпуске

Форма эмитента повторяет структуру «Решения о выпуске» оператора ИС и адаптирована под **долговые ЦФА** с фиксированным доходом.

| № | Раздел | Что заполняется |
|---|---|---|
| 1 | Эмитент | ЮЛ: полное наименование, дата ОГРН, бенефициар. ИП: ФИО, дата ОГРНИП, бенефициар — подставляются из анкеты. **Сайт эмитента** — обязателен, либо отметка «Сайта нет» (Решение публикуется на сайте эмитента) |
| 2 | Оператор ИС | автоматически |
| 3 | Вид и объём прав | наименование, **ставка % годовых**, **частота выплат**, **дата погашения** (обязательна), порядок погашения. Конструктор сам собирает **формулу купона** и **плановый график** и вставляет **обязательные положения долговых ЦФА** |
| 4 | Количество | минимум и максимум выпуска, минимум и максимум в одной заявке |
| 5 | Цена | цена 1 ЦФА = номинал; объём считается на лету |
| 6 | Период размещения | даты начала и окончания приёма заявок |
| 7 | Признание состоявшимся | автоматически из минимума |
| 8 | Смарт-контракт | готовый текст, не редактируется: размещение, возврат денег, выплаты и погашение выполняет смарт-контракт |
| 9 | Оплата | цифровые рубли кошелька (DvP) или безналичные |
| 10 | Обеспечение | Нет · Поручительство · Залог · Гарантия; если не «Нет» — кто обеспечивает (название, ИНН), что именно, условия |
| 11 | Ответственность | переключатель «Не ограничена / Ограничена»; если ограничена — чем именно |
| 12 | Круг лиц | Все пользователи (физлицам — до 600 тыс. ₽ в год) · Только ИП и компании · Только квалифицированные инвесторы |
| 13 | Выкуп эмитентом | да / нет + условия |
| 14 | Иные условия | досрочное погашение, споры |
| 15 | Риски и подпись | не меньше трёх рисков; подпись эмитента; **подпись лица, давшего обеспечение**, — если в п. 10 не «Нет» |

**Долговые ЦФА (259-ФЗ ст. 3 ч. 1.2; после перехода на 282-ФЗ — ст. 7 ч. 15).** Четыре фразы конструктор вставляет в документ сам —
эмитент их не пишет и не может удалить: ЦФА являются долговыми; изменение вида и объёма обязательств не допускается; каждый ЦФА
удостоверяет одинаковые условия независимо от даты покупки; если эмитент становится обладателем ЦФА, записи о них погашаются.
Пункты «порядок и сроки исполнения» и «порядок определения выплат» собираются из полей раздела 3: в документе — формула
`Купон на 1 ЦФА = Цена × ставка × дни периода / 365` с цифрами и таблица графика (план — если сбор закроется в последний день приёма
заявок; периоды отсчитываются от даты DvP по тем же правилам, что у сторожа выплат). Дата погашения обязательна: долг «без срока
погашения» можно продавать только квалифицированным инвесторам (Указание ЦБ 7176-У).

**Проверка перед отправкой.** Внизу формы — «Не хватает: …» со ссылками на незаполненные поля; кнопка «Подписать и отправить на
модерацию» неактивна, пока список не пуст (поля скрытых блоков — например, обеспечения при «Нет» — не требуются).

**Круг лиц на витрине.** У выпуска значок «Для ИП и компаний» или «Для квал. инвесторов»; для тех, кому покупать нельзя, кнопка
«Купить» неактивна и подписана причиной. Сервер проверяет то же самое при заявке; «только квалифицированные» дополнительно
проверяет смарт-контракт.

**После одобрения** на карточке выпуска, странице выпуска и в «Моих выпусках» — значок «Опубликовано»:
«Решение о выпуске опубликовано dd.mm.yyyy · открыть PDF».

Сервер проверяет всё, включая логику: максимум ≥ минимуму, начало размещения не раньше сегодня, окончание не раньше начала и не дальше года, погашение позже окончания размещения и не дальше 10 лет.

При отправке считается **SHA-256 канонического JSON документа**. Хэш печатается в PDF и записывается в смарт-контракт при одобрении, так что любой может убедиться, что выпуск соответствует именно этому документу.

### Условия выпуска и как они исполняются

Условия из Решения о выпуске исполняются тремя способами.

| Раздел | Условие | Кто исполняет | Как |
|---|---|---|---|
| 4, 7 | Выпуск состоялся, если собран минимум | ⚙ смарт-контракт | `finalize`: собрано ≥ минимума — ЦФА всем инвесторам и деньги эмитенту одной транзакцией (DvP), меньше — возврат всем |
| 4 | Максимальный объём | ⚙ смарт-контракт | `subscribe` отклоняет заявку сверх объёма |
| 5 | Цена 1 ЦФА | ⚙ смарт-контракт | в холд уходит ровно количество × цена |
| 9 | Способ оплаты | ⚙ смарт-контракт | цифровые рубли блокируются в контракте до закрытия сбора |
| 12 | Круг лиц | ⚙ контракт + 🖥 платформа | белый список и флаг квалификации — в контракте; «только ИП и компании» и лимит 600 000 ₽ — на сервере |
| 6 | Период размещения | 🖥 платформа | заявки принимаются только в эти даты |
| 4 | Размер одной заявки | 🖥 платформа | минимум и максимум в одной заявке |
| 3 | Купоны и погашение | ⚙ смарт-контракт + сторож | график в контракте; в дату выплаты сторож отправляет транзакцию, контракт проверяет дату и деньги эмитента и зачисляет всем владельцам; не хватает денег — выплата не проходит и становится просроченной |
| 13 | Выкуп | 📄 эмитент | обязательство купить ЦФА до погашения на указанных условиях |
| 10 | Обеспечение | 📄 эмитент + лицо, давшее обеспечение | поручительство, залог или гарантия оформляются отдельным договором; это лицо тоже подписывает Решение |
| 14 | Досрочное погашение | 🖥 платформа + ⚙ контракт | если не предусмотрено — платформа не даст погасить раньше даты погашения |
| 11, 14 | Ответственность и споры | 📄 эмитент | претензия эмитенту, затем суд |

«Обязательство эмитента» не значит «необязательно»: условия подписаны УКЭП, их хэш лежит в контракте, и нарушение — основание для претензии и иска. Но исполняет их не код, а эмитент; суд — если эмитент не исполнил. Выкуп и обеспечение учитываются в оценке выпуска 0–100.

### Купоны и погашение: сторож выплат (`keeper.py`)

Смарт-контракт не запускается сам: код в EVM выполняется, только когда кто-то отправил транзакцию. Поэтому, как и в настоящих системах (Chainlink Automation, «сторожа» операторов ИС), выплаты по датам отправляет **сторож** платформы, а **правила проверяет контракт**.

1. При DvP график купонов записывается в контракт (`setSchedule`): даты выплат — 00:00 по Москве, шаг 1 или 3 месяца от даты DvP, хвост короче 15 дней — к последнему периоду.
2. Сторож регулярно смотрит выпуски в обращении. Наступила дата — отправляет `payCoupon`, в дату погашения после последнего купона — `redeem`. Если сервер был выключен, при следующей проверке догоняет все пропущенные даты по порядку.
3. Контракт сам отказывает, если дата не наступила, порядок нарушен или у эмитента не хватает цифровых рублей. Раньше срока не заплатит никто: ни сторож, ни эмитент.
4. **Нет денег — нет выплаты.** Выплата не проходит целиком, становится «Просрочено» у эмитента и инвесторов, эмитенту раз в день приходит напоминание в историю операций. После пополнения кошелька сторож выплатит при следующей проверке; эмитент может нажать «Выплатить сейчас».
5. **Досрочное погашение** — только если разрешено РоВ (раздел 14): владельцы получают номинал и купон, накопленный в текущем периоде, остальные купоны отменяются.

Сумма каждому владельцу — `qty × номинал × ставка × дни / 365`, вниз до рубля; так же считает `couponOf` в контракте, поэтому сверка сходится до рубля.

**Как запускается сторож** (одновременно безопасно — дважды одну выплату не провести: уникальный индекс в базе и проверка порядка в контракте):

| Способ | Когда | Настройка |
|---|---|---|
| Фоновый поток | `python main.py` — локальный запуск | `KEEPER_INTERVAL` секунд, по умолчанию 60; `0` — выключить |
| При запросах к сайту | любой хостинг, в том числе без потоков и расписаний | `KEEPER_REQUEST_INTERVAL` секунд, по умолчанию 300; `0` — выключить |
| Команда | cron, планировщик задач Windows | `flask --app main keeper` — один проход, `--loop 60` — постоянно |
| Кнопка | админ-панель → «Сторож выплат» → «Проверить сейчас» | там же — ближайшие выплаты и журнал сторожа |

Если сторож и сайт работают в разных процессах, сайт замечает чужие транзакции в журнале и догоняет встроенную сеть (воспроизводит только недостающий хвост).

## 📜 Бизнес-правила

### Покупка — `buy_cfa_on_showcase` (и `subscribe` в контракте)

| Проверка | Для кого |
|---|---|
| Участник допущен администратором | все |
| Выпуск в статусе «Сбор заявок», сегодня — внутри периода размещения | все |
| Количество в пределах «минимум / максимум в одной заявке» и остатка объёма | все |
| Эмитент не покупает свой выпуск | все |
| Хватает свободных средств | все |
| Выпуск не «только для квалифицированных» | ФЛ без квалификации |
| Годовой лимит 600 000 ₽ | ФЛ без квалификации |
| Код ПЭП = `1234` / непустой код УКЭП | ФЛ / ЮЛ |

### Закрытие сбора — `finalize_issue_dvp`
Собрано не меньше минимума → ЦФА в портфели, деньги эмитенту (`ISSUED`). Иначе — возврат денег **и годового лимита** физлицам (`CANCELLED`). Одновременно — `finalize()` в контракте.

### Журнал-цепочка — `append_ledger_block`
`tx_hash = "0x" + SHA-256(prev_hash | user_id | op_type | amount | description | timestamp)` — каждый блок ссылается на предыдущий. Рядом хранится хэш реальной транзакции EVM.

## 📝 Регистрация и проверка анкеты

Правила записаны дважды, с одинаковыми текстами ошибок: в `static/app.js` для подсветки сразу и в `validators.py` как главный «судья».

| Поле | Правило |
|---|---|
| Логин | 3–32 символа `a-z 0-9 _ . -`, регистр не важен, уникален |
| Пароль | 8–64 символа, буква и цифра; повтор совпадает |
| Тип участника | вкладки «Для физ лиц» и «Для юр лиц»; на вкладке физлица первым идёт выбор «Вы ИП? Нет / Да» |
| ФИО | 2–4 слова, буквы и дефис |
| Дата рождения | календарь, 18–120 лет |
| Место рождения | подсказки городов, можно своё |
| Город регистрации / юр. адреса | **только из справочника** |
| Улица, дом | буквы и номер дома |
| Паспорт (ФЛ, ИП и представителя ЮЛ) | **ровно 10 цифр**, символы ввести нельзя |
| Телефон, e-mail | `+7` и 10 цифр; `user@example.ru` |
| ИНН / СНИЛС | 12 / 11 цифр; ИНН уникален |
| Сокращённое наименование ЮЛ | начинается с формы собственности: `ООО`, `АО`, `ПАО`…; «ИП …» отправляется на вкладку ИП |
| ОГРН, ИНН/КПП, счёт, БИК | 13 цифр; `10 / 9` цифр; 20 цифр; 9 цифр с `04` |
| ИП: личные данные | та же анкета физлица (ФИО, паспорт, ИНН, СНИЛС, адрес — это место жительства ИП) |
| ИП: ОГРНИП, дата регистрации | появляются при «Да, я ИП»: 15 цифр, начинается с `3`; не позже сегодня |
| ИП: расчётный счёт, БИК | 20 цифр, начинается с `40802`; 9 цифр с `04` |
| ИНН представителя | ровно 12 цифр |

Формат проверяется при регистрации, а контрольные суммы — в автосверке администратора. Так тестовые данные проходят регистрацию, а администратор видит, что они не настоящие.

## 🔌 HTTP API

Все `POST` принимают и возвращают JSON. Ошибки: `{"status": "error", "message", "errors": {поле: текст}}`.

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/api/register` | все | `{role: "fl"\|"ul", fields}` → участник в статусе «На проверке» |
| `POST` | `/api/login` | все | `{login, password}` → `{redirect}` (админа — в `/admin`) |
| `GET` | `/api/issues` | все | опубликованные выпуски |
| `POST` | `/api/issues` | допущенное ЮЛ | подать Решение о выпуске (поля формы РоВ) |
| `POST` | `/api/issues/<id>` | эмитент | исправить РоВ (на проверке / на доработке) |
| `POST` | `/api/issues/<id>/finalize` | эмитент выпуска | закрыть сбор: DvP или возврат |
| `POST` | `/api/issues/<id>/coupon` | эмитент выпуска | выплатить наступивший купон сейчас, не дожидаясь сторожа |
| `POST` | `/api/issues/<id>/redeem` | эмитент выпуска | погасить: в дату погашения или досрочно, если разрешено РоВ |
| `POST` | `/api/admin/keeper/run` | админ | проход сторожа выплат сейчас |
| `POST` | `/api/buy` | допущенный | `{issue_id, qty, sign_code}` |
| `POST` | `/api/deposit`, `/api/withdraw` | допущенный | `{amount_rub}` |
| `POST` | `/api/admin/users/<id>/approve` · `reject` · `block` | админ | `{reason}` (для отказа и блокировки обязательна) |
| `POST` | `/api/admin/issues/<id>/approve` · `reject` | админ | `{reason}` |
| `POST` | `/api/admin/benchmarks` | админ | рыночные ориентиры (`key_rate`, `deposit_rate`, `inflation`, `ofz_curve`, …) или `{reset: true}` |

Каждый успешный ответ операции содержит `tx_hash` (журнал платформы) и `evm_tx_hash` (транзакция в блокчейне).

**PDF:** `/docs/issues/<id>/decision.pdf` · `results.pdf` · `registry.pdf` · `/docs/statement.pdf` · `/docs/orders/<id>.pdf` ·
`/admin/users/<id>/application.pdf` · `/admin/reports/participants.pdf` · `/admin/reports/reconciliation.pdf`

| Код | Когда |
|---|---|
| `400` | ошибка данных или правило бизнес-логики / контракта |
| `401` | не выполнен вход |
| `403` | нет прав: не допущен, не эмитент выпуска, не администратор |

## 🛡 Безопасность

**Что сделано:**

- 🔑 Пароли — только хэш scrypt; одинаковое сообщение при неверном логине и пароле; сессия очищается при входе
- 🧑‍⚖️ Ролевой доступ: участник / эмитент / администратор; операции — только после допуска
- 📝 Решения администратора с обязательной причиной отказа и полным журналом аудита
- 💉 Параметризованные SQL-запросы; белые списки вкладок и статусов
- 🧱 `CHECK` / `UNIQUE` / `FOREIGN KEY` в базе, включая `collected_qty <= max_qty` против перебора объёма
- ⛓ Правила продублированы в смарт-контракте; хэш документа выпуска хранится в блокчейне
- ⚛️ Атомарность: контракт вызывается последним, его отказ откатывает SQLite; самовосстановление EVM
- 🧼 Пользовательский текст в PDF и подсказках экранируется (защита от XSS и разметки)

> ⚠️ **Это прототип для хакатона, не production.** Перед реальным использованием нужны: секретный `SECRET_KEY`,
> выключенный `debug`, CSRF-токены, ограничение попыток входа, HTTPS, настоящие ПЭП/УКЭП, платёжный шлюз
> и хранение ключа оператора в HSM.

## 📱 Адаптивная вёрстка

Все правила — в `static/responsive.css`, он подключается последним и не меняет десктопный макет.

| Ширина | Что меняется |
|---|---|
| ≥ 1680 px | шире контейнеры, витрина в 4 колонки (≥ 2200 — в 5) |
| ≥ 1280 px | картинка витрины справа в своём размере (1024 px), слева — фирменный градиент: не растягивается и не мылится |
| 1024–1279 px | узкое боковое меню |
| < 1024 px | меню разделов кабинета и админки — лента вкладок под шапкой, активная вкладка прокручивается в видимую область |
| < 640 px | компактная шапка («Рынок», «Кабинет», «Админка»), отдельный кадр картинки, кнопки во всю ширину, поля ввода 16 px (iOS не увеличивает страницу), окна покупки и кошелька — снизу экрана |

**Таблицы** подстраиваются под ширину самой панели (CSS container queries), а не экрана: уже 780 px — плитки, уже 560 px — карточки
«подпись — значение». Подписи столбцов `app.js` берёт из заголовков таблицы (`labelTables`), поэтому шаблоны таблиц не менялись;
таблица с классом `ui-table--plain` остаётся таблицей. **Графики** рисуются под ширину блока и перерисовываются при повороте экрана.

**Анимации — только где помогают:** окно покупки и кошелька появляется (на телефоне — выезжает снизу), уведомление выезжает,
поля по выбору в Решении о выпуске плавно раскрываются, кнопка слегка откликается на нажатие. Всё ≤ 0,22 с и выключается системной
настройкой «Уменьшить движение» (`prefers-reduced-motion`). Картинка витрины на компьютере — как в исходном макете, во всю ширину.

Проверено автоматически на 8 ширинах (360, 390, 768, 1024, 1280, 1440, 1920, 2560) по 29 страницам: нигде нет горизонтальной прокрутки
и вылезающих за экран элементов.

```
Браузер ──80──▶ nginx ──▶ gunicorn 127.0.0.1:8000 (main:app, служба cfa-web)
                  └── /static/ отдаёт сам
                 сторож: flask --app main keeper --loop 60 (служба cfa-keeper)
                 оба процесса работают с одним cfa.db; сайт подхватывает транзакции сторожа из журнала
```

1. **Ключ SSH** (на своём компьютере, PowerShell): `ssh-keygen -t ed25519` → Enter до конца. Публичный ключ — файл
   `C:\Users\<вы>\.ssh\id_ed25519.pub`, его содержимое загружается в консоль Cloud.ru.
2. **ВМ**: console.cloud.ru → «Инфраструктура» → «Виртуальные машины» → «Создать». Образ — Ubuntu 22.04 (или 24.04),
   конфигурация free tier, сеть — с **публичным IP**, аутентификация — публичный ключ из шага 1.
3. **Группа безопасности**: входящие TCP 22 (SSH), 80 (HTTP), при необходимости 443 — источник `0.0.0.0/0`; исходящие — любые.
4. **Подключение**: `ssh <логин>@<публичный IP>`.
5. **Установка** на ВМ (репозиторий закрытый — вместо пароля GitHub спросит токен, Settings → Developer settings → Personal access tokens):
   ```bash
   sudo apt-get update && sudo apt-get install -y git
   git clone https://github.com/KISEL4KO/VTB_Hack.git
   cd VTB_Hack && bash deploy/cloudru/setup.sh
   ```
   Скрипт ставит nginx и зависимости, создаёт `/etc/cfa.env` со случайным `SECRET_KEY`, базу с демо-данными
   (`SEED=0 bash deploy/cloudru/setup.sh` — пустая база), службы `cfa-web` и `cfa-keeper` и печатает адрес сайта.
6. **Обновление**: `bash deploy/cloudru/update.sh` (`RESET_DB=1 bash deploy/cloudru/update.sh` — если менялись схема базы или контракт).

Логи: `journalctl -u cfa-web -f`, `journalctl -u cfa-keeper -f`. Gunicorn запускается одним процессом (с потоками):
встроенная EVM живёт в памяти процесса, лишние воркеры были бы лишними копиями цепочки. Сайт и сторож вместе занимают около 200 МБ памяти.

Сама ВМ на free tier бесплатна, а публичный IP оплачивается отдельно — по тарифу Evolution Compute 0,2074 ₽/час с НДС
(≈150 ₽ в месяц), в том числе пока ВМ выключена. Без публичного IP сайт снаружи не открыть.

## 🚧 Известные ограничения прототипа

| Что | Подробности |
|---|---|
| Подписи | СМС-код ПЭП всегда `1234`, «УКЭП» — хэш, а не криптографическая подпись |
| Пополнение | Деньги появляются без реального платежа (в контракте — выпуск токенизированных рублей) |
| Сторож выплат | Работает, пока работает сервер (или по расписанию); в настоящей системе это отдельный отказоустойчивый сервис. НДФЛ с купонов не удерживается |
| Аналитика | Модель без учёта кредитного рейтинга эмитента и ликвидности; ориентиры обновляются вручную |
| Внешний узел и откат | Самовосстановление работает во встроенной сети; во внешней сети отменить уже исполненную транзакцию нельзя |
| Масштаб | `finalize()` перебирает инвесторов в одном цикле — для тысяч инвесторов нужна пакетная обработка |
| Проверка журнала-цепочки | Время из хэша блока не сохраняется — цепочку `blockchain_ledger` нельзя пересчитать (реальную неизменяемость обеспечивает EVM-журнал) |
| Адреса | Подсказки только по городам, улица вводится вручную |
| ИП и физлицо | ИНН уникален, поэтому один человек не может одновременно иметь кабинет физлица и кабинет ИП |
| Закрытие сбора | Эмитент может закрыть сбор в любой момент периода размещения; автоматического закрытия по дате нет |
| Миграции | Нет: при изменении схемы базу нужно пересоздать |
| Тесты | Автотесты есть только для аналитики (`tests/test_analytics.js`); остальное проверено скриптами вручную |
